# 统一撤销与本机交付设计

日期：2026-09-18。基线：78053688fe4026ef13415559f321569b08ec0ebd。

## 授权与边界

用户已选择“采用统一撤销”，随后要求“继续执行，不要断断续续，你负责全盘操作，直至项目完整落地（模型接口配置保留）”。这确认了已展示的五项撤销规则，并要求后续规格、计划、实现及自动验证连续执行，不再设置人工逐项审阅或手动测试关卡。技术细节由实施者负责，变更须可审查、可恢复。

本次完成已有 Windows 本机单用户应用，不把它改成未经设计的公网多用户服务。不配置密钥、不调用真实模型、不产生模型费用、不安装或升级依赖、不推送远端、不改变防火墙。保留 Qwen 接口和设置入口。真实模型质量、全新 Windows 系统安装、公网邀请版没有本次证据时必须明确未验证/未交付，不能用离线测试替代。

## 1. 用户行为

入口统一为“撤销上一次修改”，明确显示最近记录的类型和对象。每次仅撤销当前目标最近一次支持撤销的修改。任务状态和实际分钟恢复其原值；打卡/阻碍记录标记为已撤销，原内容保留。撤销反馈不顺带撤销另一次任务修改、完成证据或已批准计划。

允许状态沿用 active、reviewing、paused。待批准计划等状态下不绕过现有状态机。最近记录若已不适用，应显示原因，不跳过它偷偷撤销更早记录。新的界面请求绑定展示的记录 ID 和目标版本；过期页面收到冲突，必须重新读取；重复请求只能返回同一次结果。

## 2. 持久化与旧数据

扩展现有 undo_records 为统一日志：kind 为 task_execution 或 check_in，task_id/check_in_id 对应唯一目标，每个 owner+goal 使用递增 ordinal。新增 check_ins.withdrawn_at 可空字段。所有记录仍保留正反补丁及 undone_at；反馈补丁不包含用户文本。数据库和仓储共同校验目标形状、同一 owner/goal 和记录唯一性。

新增迁移，不改写 0000 历史迁移。保留旧任务撤销记录 ID、补丁、版本、完成撤销状态；为已有打卡补建日志，初始未撤销。旧记录按 created_at、来源顺序、原表 rowid 排序；时间完全相同时任务修改在前、打卡在后，即先撤销打卡。旧库无法证明跨表的同时间先后，不假装恢复它。新记录在事务中分配 max(ordinal)+1，时间回拨也不能改变顺序。

反馈撤销允许引用历史计划的任务，只校验反馈所属目标/用户；任务撤销保留当前批准计划与正向状态匹配检查。新外键要求清除/删除先删除撤销日志，再删除打卡，保留既有可信确认路径。

## 3. 服务、接口与重放

统一 UndoService 按 kind 分派，任务或反馈更新、undo 标记、目标版本、派生信号与审计在同一事务中成功或全部回滚。反馈写入和其撤销日志也在同一事务内产生，不重复记录重放请求。domain-write-observer 必须记录反馈撤销，防止 Agent 在写入后误重试。

公开共享 UndoResultSchema 接受旧的 `{ task }` 结果和新的 `{ checkIn }` 结果。不得修改历史 operations.parameter_hash/result。旧的 record_check_in 结果缺少 withdrawnAt 时按 null 读取；创建输入必须排除这个服务端字段。给撤销工具新增可选 expectedUndoId、expectedGoalVersion，不使用会改变旧输入哈希的默认值；两者必须成对出现。旧请求仍可精确重放；新 UI 总是携带两者。旧式无绑定的新请求保留“事务内最近记录”的兼容语义，不作为新 UI 路径，模型上下文与工具说明应提供/要求使用当前候选绑定。

工作区提供候选描述及不可撤销原因，canUndo 保持兼容布尔值。候选判断和真正执行使用同一验证逻辑，避免按钮允许运行而服务器拒绝的常规分歧。工具状态、明确用户意图、来源校验仍生效。

Agent 对话中成功执行撤销后，当前轮直接通过现有成功持久化路径返回确定性确认，不继续执行同批剩余工具、不再请求模型或对话压缩。确认不带被撤销反馈的正文。这样既有内存中的旧对话和工具返回的历史记录不会在同一轮绕过上下文分界再次发送。

其他页面在当前对话进行中撤销反馈时也适用同一边界：缓存上下文须绑定构建时的分界版本，在后续模型调用、超时重试及使用旧响应执行工具前校验。发生变化则安全终止旧轮次，不得等最终目标版本冲突才阻止写入；已发生请求的用量仍应记账。历史成功结果精确重放不能因页面刚刷新到新版本就被标记为当前建议；新鲜度必须来自原始结果对应的上下文或独立服务端事实，历史结果字节及哈希保持不变。

## 4. 有效反馈与历史记忆

planningProjection 分离完整历史与有效反馈。有效反馈首先排除 withdrawnAt 非空记录，再执行已有任务沿袭/执行重置投影。planningFacts、偏好推导、重规划触发、复盘中的阻碍摘要、真实模型上下文与 LocalMockModelClient 的独立快照都使用有效反馈。历史列表/导出保留标记；导出格式升级为 schemaVersion 2，包含 withdrawnAt、conversationMessages 与保留的历史摘要，并说明与 1 的差异。

上下文分界使用仅服务端可见的日志元数据 conversationFence：每目标递增的 revision、可空 throughMessageId、可空 throughAgentTurnOperationId。revision 按撤销发生顺序增长，不按被撤销日志的 ordinal 或时间排序；无历史消息时保留 revision 但消息分界为空。后一个 ID 记录当时最近的成功 Agent 对话操作，按操作插入顺序判定旧复盘是否过期，避免根据重复文本或时钟猜测。此元数据不暴露原始 Operation 内容。

已经生成的建议不被改写为新的模型结论。撤销反馈后旧建议显示为历史或移出当前建议卡，后续显式请求依据有效记录计算，不自动调用模型。历史对话可能含已撤销反馈，因此仅过滤结构化打卡不够：在撤销事务中持久记录当时最后一条对话的 ID 作为上下文分界。后续模型请求不再带分界前的消息/摘要；历史记录本身不删除。新消息继续正常参与上下文和压缩，压缩提交必须校验分界未变化，防止并发压缩把旧反馈带回来。无历史消息时，分界不应误排除未来消息。已有批准计划及设置界面可编辑的时间窗口、有效策略保持不变。估时偏差、任务粒度、常见阻碍继续按现有规则从有效记录重算；现有 API 虽允许写入这三个推导字段，其值一直可能被后续执行操作重算，本次不引入手动覆盖来源管理。
